# ev3_client Application

> **Novedades:** voz que funciona sin internet, botón tocar-para-hablar, acciones sociales, emociones y nueva interfaz. Ver [CAMBIOS.md](CAMBIOS.md).

## Summary
This project is a client application to control an EV3 LEGO Mindstorms robot. Note that this app was designed and tested in Android; while the whole app is written in Flutter, there's no guarantee that it will work in other platforms.
This application was designed following a client-server architecture, with the server being a Python script running on the robot on top of the ev3dev software. The communication is handled in typical client-server fashion, sending messages back and forth between the two as needed; the specifics are detailed below.

## Robot's physical configuration
The current build ensues a tank-like configuration with a vertical claw attached to the back and an infrared sensor facing front. Movement is handled with two large motors that move continuous tracks located at each side, while the claw is attached to a medium motor that handles it's movement.

## Requirements
The application depends on a few external factors:
1. The robot runs ev3dev.
2. The robot is tethered to the device running the application via Bluetooth **Internet hotspot**.
3. The robot runs a custom Python "server" that listens to instructions from the app.
4. Gemini LLM (for voice commands).
5. Internet availability (to reach Gemini).

**Update:** Gemini no longer provides a generous free tier on their API like before. Depending on the model, you'll likely be limited to 10-20 requests per day.

### Caveats
- The app's dependency on the robot running specific software makes it not very accessible for the average user, nor easily portable to similar devices (as in, other robots, even within the Mindstorms product line). Although specific instructions may be provided, it'd still prove a tedious task to set everything up for the first time, and it also requires a MicroSD card (for running ev3dev) which might not be immediately available.

- Since the server is specifically designed for this particular configuration of the robot, it may not work properly with different (physical) builds of the LEGO robot. Sensor info should be able to be read despite the configuration, but currently it's not used for any purpose.

- While Gemini is the easiest to use LLM to normalize the instructions into something the robot can read (due to free usage and being hosted by Google), it introduces another set of issues, namely the need for an API key and the limitations of the free tier. Currently a personal API key is being used. Consider setting up a proxy server to avoid exposing the key.

## Robot communication
The server listens to instructions sent from the app via TCP sockets and execute them in the robot. Similarly, all relevant data is sent back to the app (sensor/odometry data).Given the protocol, it is possible for some instructions to be concatenated when sent while sending several in quick succession (e.g. Joystick movement), but given the nature of the instructions, this is not an issue, as we can safely ignore older movements.

Contrary to a common client-server architecture, as much preprocessing as possible is delegated to the app instead of the server, given the limited computing power of the smart brick housing the server software.

### Client(app)-side processing
Specifically, the following data is processed in the app before being sent to the server:
- Joystick movement: The movement vector generated by the joystick is rounded to a specific number of decimal places previous to sending it to the server. Since all data is sent as a string, this saves some bandwidth.
- Voice command movement: The device's native voice recognition is used to recognize the voice command, then, Gemini is used to normalize the voice command into a set of instructions that the robot can interpret. Communication with the LLM and response preprocessing are both handled in the client device (cellphone).
- Map data: The map is created client-side utilizing the odometry data received from the robot.

### Server-side processing
To deal with the limited capacity of the server, the only data processed in it are the instructions sent from the app, and motor data used to create the odometry data. This basically boils down to string manipulation, simple math equations and sending sensor/odometry data back to the app.

## Controls
The robot is controlled by passing a set of instructions via sockets to the robot, these can be either a movement vector for joystick movement or text instructions based on a voice command.

### Instruction syntax
#### Joystick movement
For joystick movement, the syntax is `stick:<x-coordinate>;<y-coordinate>;<claw>`. Where the `x` and `y` coordinates are the components of the joystick vector, and `claw` is a boolean value represented as either a `1` or a `0`.

#### Voice command movement
For voice commands, the command is first recognized using the platform's native voice recognition. Note that this app was designed for an Android phone, so no guarantees are made for other platforms (namely, PC and web, which won't work at all), once the words are recognized they're processed by Gemini (Google's LLM, as of writing, using Gemini Flash 1.5 latest model), which returns a set of instructions, these are then mapped to single letters that represent an action to shorten the string sent and save bandwidth. The following is the mapping currently being used:

```dart
final instructionMap = {
  "adelante": "f",  //forward
  "atrás": "b",     //backward
  "izquierda": "l", //left
  "derecha": "r",   //right
  "agarrar": "p",   //pick up
  "soltar": "d"  ,  //drop
  "?": null,        //invalid
};
```

These include all movement options for the current configuration of the robot, plus control of the claw attached to the medium motor.

With the instructions mapped and shortened, they are joined into a single string with the following syntax: `text:<instruction>-[amount]-[unit][;...]` (E.g. `text:f-20-cm;l;b-3-m`).
Available units are meters, centimeters and seconds, each represented by their respective unit symbols. Currently, only `f` (forward) and `b` (backward) instructions take units, while `l` (left) and `r` (right) turn the robot in place. Units are not applicable to claw instructions which instead functions in a *toggle* fashion.

## Connecting to the robot
If the robot is already running ev3dev, and the server application has been downloaded onto its memory, you can connect to the robot by doing the following:
1. Startup the robot and wait for ev3dev's main menu.
2. Select Bluetooth and pair your device. Remember to **turn on your device's Bluetooth tethering!**
3. Once the device is paired, connect to it via the `Network Connection` option (using your device as a Bluetooth hotspot). Once connected an IP address should show up on the top left corner of the screen.
4. Run the server application via the `main.py` file.
5. Wait for the beep and the IP address to show up in the screen. This should be the same address you saw on step 3.
6. Run the phone app.
7. In the input box, write the robot's IP address and wait for it to connect. Once connected, the robot should make another beep, and it's ready to control.

For more details about ev3dev and Bluetooth tethering, visit the following [link](https://www.ev3dev.org/docs/tutorials/connecting-to-the-internet-via-bluetooth/) and read the `Android` section.

## How to use
The app was developed trying to keep user experience in mind, so it should be mostly self-explanatory via visual cues or by having the user mess around with it, but here's a brief breakdown of how to use it:

### General distribution
On the control page, the UI is distributed in the following way:
- Movement controls are located on the middle-to-bottom left side of the screen. This includes the main movement component (joystick/area/voice command button) and the mode change button (to switch between those).
- The middle-to-bottom right side of the screen contains the claw button (to toggle the claw on and off) and the voice playback button (makes the robot repeat whatever the user says to the phone).
- The top left corner contains the disconnect button.
- The top center portion holds all the sensor data received from the robot. This UI varies depending on the amount of sensors currently available to the robot, adding or removing components as needed.
- The top right corner is where the map is located.

### Moving the robot
Currently, there are 3 ways of moving the robot:
1. Using a joystick (joystick movement)
2. Using a movement area (joystick area movement)
3. Using voice commands (voice command movement)

Here's a brief breakdown of each:

#### Joystick movement
This is the most common form of movement, and it should be familiar with most users. It mimics the movement commonly used in videogames, with the robot following the joystick direction.

#### Joystick area movement
This mode is essentially the same as joystick movement, with the difference being that instead of a stationary joystick, the *movement area* is a rectangular portion of the screen where all gestures are interpreted the same as joystick movement. While this might seem redundant, it may prove more comfortable for some users.

#### Voice command movement
This mode should be very user friendly, as natural language is used to guide the robot in its movement. This mode consists of a button which can be pressed (and held) by the user in order to start recording. When the user releases the button, the words are recognized, processed by Gemini into a normalized set of instructions and sent to the robot to execute.

*Note: Due to the volatile nature of LLM's responses, it may take some time for the robot to respond and this mode is prone to errors.*

### Other actions
#### Claw
The claw can be controlled by pressing the button on the middle right portion of the screen, it's a simple toggle button.

#### Voice playback
Similar to the voice command button, the user can press and hold to start recording, once released, the words are recognized and sent to the robot as a string that it can repeat using it's speech function. Since this function depends on voice recognition, sounds that are not recognized as words will not be played back.

#### Map
Currently, the map is merely visual, and thus not interactable with by the user. It is meant to simply create a rough representation of the robot's surrounding area.

### Disconnecting
Upon pressing the disconnect button, the app will close all sockets, stopping the communication. The server application will also terminate.

### Reconnecting
In order to reconnect to the robot, the server app needs to be restarted. The app *might* need to be restarted as well, but this shouldn't be the case, if it happens, it's a bug due to state management errors.
